## 1. 用户目标与项目状态

用户希望制作一个以 DeepSeek 为模型的虚拟群友，直接在真实抖音群里参与聊天。用户不是该群群主。最终目标是实际接入抖音群，而非只做模拟聊天页面或命令行演示。

目前仅完成需求讨论和初步公开文档查询，没有项目代码、实测接入方案、抖音授权凭证或 DeepSeek API Key。本文是开发交接，不代表方案已验证可行。

### 已确认的用户要求

- 使用 DeepSeek 作为对话模型。
- 接入真实抖音群。
- 用户不是群主，不可假设有群主权限。
- 用户将转移到 Codex 继续开发，希望 Codex 读取本文后推进。

## 2. 接入事实与不确定性

### DeepSeek

官方文档提供 OpenAI 兼容的调用方式，base_url 为 https://api.deepseek.com ，对话接口为 POST /chat/completions。使用环境变量保存 API Key，模型名设为配置项，并在开发时依据官方文档核实，不要直接照抄旧教程的模型名。

来源：https://api-docs.deepseek.com/zh-cn/

### 抖音

本轮查询到字节跳动公开仓库描述的“群聊小助手”内测能力：

- 需要为指定群提交内测申请，审核后获得 access-token。
- 以群聊小助手身份发言，并标注信息来源。
- 文档标明每群每自然日最多发送 10 条消息。
- 该 README 描述主动发送能力，不能据此推断已提供普通群成员实时接收群消息的能力。

来源：https://github.com/bytedance/douyin-im-group-open-capabilities

另有面向小程序经营者的私信、群聊能力，但不能直接推断适用于普通个人账号和任意已有群。

参考：https://developer.open-douyin.com/docs/resource/zh-CN/mini-app/develop/tutorial/open-capabilities/management/private-domain/private-and-group-message

这些是本轮公开资料的查询结果，开发时应复核权限条件和当前限制。用户不是群主，因此不要把群主内测授权作为默认前提，也不要断言所有官方接入路线均不可用。

### 候选路线：界面自动化

如果没有适用官方权限，可以调查通过用户自己可正常访问的抖音网页或客户端界面收发消息。此路线尚未实测，不能承诺 Playwright、桌面自动化或某个第三方项目一定可用。

优先检查网页端群聊是否可用；可用时再评估浏览器自动化。网页端不满足需求时，再调查桌面客户端的可访问性接口；截图/OCR仅作为后备方案。不要提前编造页面选择器、窗口控件、群 ID 或私有消息接口。

登录、验证码和二次验证由用户完成。会话失效时停止并提示，避免无限重试。无需自动申请入群，也不要绕过账号或群访问限制。

## 3. 给 Codex 的推进顺序

1. 先读取现有仓库说明和 AGENTS.md，检查已有文件与运行环境，保留用户改动。
2. 先做不依赖抖音真实接入的配置、模型客户端、消息处理和测试；同时仅询问影响接入的必要信息，优先确认电脑端群聊入口。
3. 将抖音“收取一条新消息、识别发送者、定位目标群、发送一条文字”作为首要可行性验证。记录实际证据、限制和失败原因。
4. 收发路径验证通过后再接入完整聊天循环。真实发送使用用户指定的目标群和测试内容；不能把授权开发当作向未知群发送消息的授权。
5. 如果暂时无法访问用户本机，交付本地可运行的诊断入口和明确操作说明，将接入标为未验证；不要把离线演示宣称为真实群接入成功。

最终目标仍是真实抖音群。离线适配器是开发工具，不是交付终点。

## 4. 建议的第一版范围

以下是建议默认值，并非用户已确认的需求，可通过配置调整：

- 单账号、单个允许的目标群、文字消息。
- 先支持 @ 机器人或指定口令触发，后续再增加自主接话。
- 忽略自身消息、启动前历史消息、已处理消息和非目标群消息。
- 默认回复 1–3 句中文，设置明确的长度上限。
- 使用最近少量消息作为上下文，设置消息数和 token 预算。
- 群级与用户级冷却、每小时和每日发言限额。
- 支持 dry-run（只生成不发送）、暂停、停止和恢复。
- 设置可识别的 AI 身份；是否已向群友说明尚未确认。
- 暂不包含图片、语音、视频解析、自动加好友或多群推广。

## 5. 建议架构

流水线：消息适配器 → 标准化与去重 → 触发/限频判断 → 上下文组装 → DeepSeek → 输出检查 → 发送适配器 → 结果记录。

采用可替换适配器，把聊天逻辑与抖音界面细节解耦。可以先实现 ConsoleAdapter 验证核心逻辑，再实现经实测选定的 DouyinAdapter。Python 是建议技术选型，并非用户硬性要求。

建议模块职责：

| 模块 | 职责 |
| --- | --- |
| config | 配置加载、参数校验、密钥读取 |
| adapters | 接收消息、识别目标会话、发送文本 |
| policy | 自身过滤、触发、冷却、限额 |
| llm | DeepSeek 请求、超时、可控重试 |
| memory | 最近上下文、处理记录、重启恢复 |
| persona | 可编辑的人设和回复风格 |
| runner | 主循环、暂停、停止、异常处理 |

消息数据至少包含：platform、conversation_id、message_id、sender_id、sender_name、text、timestamp、is_self、mentions。未知字段保持未知，不能用昵称代替可靠用户标识。如果界面拿不到原生 message_id，需要说明替代去重方式的冲突风险，尤其不能把不同人或不同时间发送的相同文字误判成同一条。

本地状态可采用 SQLite。为消息处理状态建立唯一约束，并记录 received/generated/sending/sent/failed/unknown 等状态。发送超时可能代表已发送，不应盲目重试造成重复发言；先核实可见发送结果，不能确认则暂停该消息。不能声称 UI 自动化能保证严格 exactly-once。

## 6. 模型上下文与隐私

- 系统人设、群消息和本地配置应分开；群友文字是输入数据，不能覆盖系统规则或变成执行命令。
- 群消息不能触发 shell、文件读取、密钥输出或工具执行；这个聊天机器人默认无需执行工具。
- 仅向模型提交回复所需的近期群消息；明确告知用户消息会发送给模型服务商。
- API Key 使用 DEEPSEEK_API_KEY 等环境变量；不写入源码、日志或提交记录。
- 登录会话、浏览器配置、数据库和 .env 加入忽略规则。
- 日志默认记录消息标识、耗时和错误类别；避免默认持久化完整群聊。提供历史清理方式，长期记忆作为后续可选功能。

## 7. 配置建议

| 配置项 | 用途 |
| --- | --- |
| DEEPSEEK_API_KEY | 本地秘密，示例文件只放占位符 |
| DEEPSEEK_BASE_URL | 默认 https://api.deepseek.com |
| DEEPSEEK_MODEL | 开发时核实并配置可用模型 |
| target_conversation | 严格匹配目标群，避免仅凭可重名群名发送 |
| self_identity | 用于忽略机器人自身消息 |
| trigger_mode | 默认 mention 或 prefix |
| dry_run | 首次启动默认开启 |
| cooldown_seconds | 回复间隔，可配置 |
| hourly_limit / daily_limit | 发言限额，可配置 |
| context_budget | 上下文消息数及 token 预算 |

## 8. 验证与验收

需要覆盖关键失效场景，而不是为简单配置堆叠测试：

- 自身消息、非目标群、重复消息和历史消息不会触发回复。
- 普通群友文本中伪造系统指令，无法泄露配置或执行命令。
- API 超时或限流后不会刷屏，重试次数有界。
- 程序重启不会重发已经确认发送的回复。
- 发送结果不确定时不会直接重复发送。
- 暂停开关可阻止排队中尚未发送的回复。
- 群定位不明确、切换到其他会话或登录失效时停止发送。

真实接入验收必须在用户指定的群中验证：接收一条新消息 → 正确判断触发 → DeepSeek 生成回复 → 发送到正确会话 → 不再响应自身回复。离线测试通过和真实接入通过必须分别报告。
