# 私聊与群聊白名单

白名单位于根目录 `browser.local.json`，修改后重启主程序。主程序同时处理已启用的私聊和群聊目标：

```bash
uv run run_friend.py --live
```

当前授权范围为“高雅抖音”群及初始化时核验的 9 位成员。`test` 是当前登录账号，保留在成员名单中但 `is_self=true`、私聊 `enabled=false`，避免向自己回复；其余 8 位可接收私聊回复。

## 配置结构

`whitelist` 保存私聊对象，使用 `sec_uid` 加 `douyin_id`（抖音号）核验；从群成员界面导入的用户也可用原生 `user_id` 加 `sec_uid` 核验。`user_id` 是平台用户 ID，不是抖音号，不能混填。未出现过的私聊不会自动新建或主动发送，等待它出现在最近会话列表后才开始采集；某个会话不存在不会阻断其他目标。

`group_whitelist` 是单独的群授权列表：

```json
{
  "kind": "group",
  "name": "高雅抖音",
  "group_id": "7516934184514961957",
  "enabled": true,
  "members": [
    {"name": "成员昵称", "user_id": "平台用户ID", "sec_uid": "平台sec_uid"}
  ]
}
```

群 ID 必须来自页面绑定数据，不能用昵称或本地指纹替代。`members` 是该群允许自动回复的发送者名单；以后入群的新成员不会自动获准。`enabled=false` 可停用一个目标。更换登录账号后，`owner_user_id` 不匹配会阻止目标核验，应重新手动核对身份和授权配置。

## 回复与数据隔离

- 群消息按气泡对应的原生消息 ID、发送者 ID 和当前群 ID 核验，不根据昵称、头像或气泡左右位置猜身份。原生身份缺失时等待，不发送。
- 仅回复名单成员的新文字来信；其他成员、本人和媒体消息不创建回复任务。自身消息以平台身份/方向排除，不依赖 `[AI]` 前缀；普通用户以该标记开头的提问仍正常处理。
- 一个任务只包含同一人的连续来信，不把两个人的需求或记忆混成一份。模型上下文中保留每条群消息的发送者。
- 群成员记忆沿用 `state/memory/groups/<群指纹>/<成员指纹>/`，与该用户的私聊记忆隔离。关键词召回和 0.33 随机门控同样适用。
- 群首次运行建立历史基线，默认不回复已经加载的旧消息。已存在检查点时恢复增量；不删除检查点或发送回执来重新测试。
- 群发送也执行草稿、源消息、群身份核验、唯一按钮点击和页面确认；人工用登录账号回复后取消对应任务。未知发送仍阻断整个发送队列，不自动重试。
- 全局至少间隔 5 秒发送。当前每小时 30 条、每天 100 条限额对群会话整体计数，不是群内每个人各有一份配额。

主程序只读取已授权群，不会修改群设置、邀请成员或自动扩大白名单。初始化脚本仍只负责读取与写记忆，是否自动群回复由本文件中的显式授权决定。

## 某个会话等待时

`observation_waiting` 会带上目标名称。单个会话的历史对齐失败只暂停该会话，不会中断后续群聊或其他联系人采样。

媒体有原生消息 ID 时，表情或视频从占位状态加载完成不会当作新消息或历史重排。程序单独保存观察指纹，与原有消息指纹、游标和发送回执分开；旧游标只有在保存快照与其完全一致时才能升级。文字内容改变、缺失原生标识或真实歧义仍保持阻断，不会通过清空游标来绕过。
